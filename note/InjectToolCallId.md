`InjectedToolCallId`는 LangChain 및 LangGraph 환경에서 **LLM에게는 파라미터를 숨기고, 실행 시점에 프레임워크가 툴 호출의 고유 ID를 자동으로 주입(Inject)하도록 지시하는 특별한 타입 어노테이션**입니다.

쉽게 말해, "이 파라미터는 LLM이 추론해서 넣는 값이 아니라 시스템이 알아서 채워줄 메타데이터이니, LLM에게 전달되는 API 스펙(스키마)에는 포함시키지 마라"라는 뜻입니다.

### 왜 `InjectedToolCallId`가 필요한가요?

제시해주신 `human_review` 코드처럼 인간의 승인이나 피드백을 받는 **Human-in-the-Loop (HITL)** 패턴을 구현할 때 필수적인 역할을 합니다. 백엔드 시스템 설계 관점에서는 일종의 Correlation ID (상관관계 식별자)라고 볼 수 있습니다.

**1. 상태 매핑 및 추적**
LLM이 특정 도구를 호출할 때마다 `call_abc123`과 같은 고유한 `tool_call_id`가 생성됩니다. 실행이 일시 중지(Interrupt)된 후, 사용자가 피드백을 입력하여 시스템을 재개(Resume)할 때, 프레임워크는 이 피드백이 **수많은 요청 중 정확히 어떤 툴 호출에 대한 답변인지** 알아야 합니다. 이 ID가 없으면 메시지의 흐름이 꼬이거나 LLM이 응답을 매핑하지 못해 에러가 발생합니다.

**2. 할루시네이션 방지 및 보안**
만약 `InjectedToolCallId`로 감싸지 않고 그냥 `tool_call_id: str`로 선언한다면, 프레임워크는 이를 LLM이 직접 채워야 하는 일반 파라미터로 인식합니다.

* LLM이 임의의 가짜 ID를 생성(할루시네이션)하여 시스템에 주입하려 시도할 수 있습니다.
* 불필요한 파라미터가 프롬프트 토큰을 낭비하게 됩니다.

### 내부 동작 흐름

1. **LLM:** "인간의 리뷰가 필요하군. `human_review` 툴을 호출해야겠다." (이때 프레임워크가 `tool_call_id: "call_xyz789"`를 생성)
2. **실행 환경:** 툴 실행 전, 프레임워크가 `Annotated[str, InjectedToolCallId]`를 확인하고, `tool_call_id` 파라미터 위치에 `"call_xyz789"`를 안전하게 꽂아 넣음.
3. **인간 개입:** 시스템이 멈추고 사용자가 `human_feedback` (예: "승인함")을 입력.
4. **재개 및 반환:** 툴이 종료될 때 생성된 결과물(`ToolMessage`)에 이 ID를 묶어서 반환함으로써, LLM이 자신의 원래 요청에 대한 정확한 답변임을 인식하고 다음 프로세스를 진행함.

결론적으로, 외부(사용자/LLM)의 간섭 없이 시스템 내부적으로 안전하게 상태 추적을 하기 위한 장치입니다.
